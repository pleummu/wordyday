## Phase Goal

**As a** player on any device or assistive technology, **I want to** play in a theme and palette that suits my eyes, learn the rules on my first visit, hear each guess result and play entirely by keyboard, **so that** the game feels soft and polished and I can share a link that previews well.

(Derived from the ROADMAP Phase 7 goal "The game looks soft and polished in every theme, works for screen-reader and keyboard-only players, and is ready to be linked publicly", which is not in user-story form; same practice as Phases 5 and 6.)

<objective>
User story slice: **As a** returning player, **I want** my save to carry my appearance choices and whether I have seen How-to-play, **so that** the update keeps all my games and shows the rules to me exactly once.

This plan lays the one save migration the phase needs (v2 to v3, all three fields at once so players never go through two migrations) and the store logic for the Help dialog, plus the test hook that keeps every existing E2E spec green once Help auto-opens. It writes the failing How-to-play E2E first (MVP rule). It deliberately does NOT call maybeOpenHelp from boot or any action: with no modal rendered yet, a 'help' dialog would silently block input for real players. 07-03 renders the modal and wires every call site in one go.

Purpose: UI-04 foundation (D-08, D-09), persistence for UI-02/UI-03 (D-04).
Output: test hook + helpers, RED e2e/help.spec.ts, save v3, store fields/actions, updated fixtures.
</objective>

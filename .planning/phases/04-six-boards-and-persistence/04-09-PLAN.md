## Phase Goal

**As a** player, **I want to** keep a separate saved game on each of the six Boards that survives refreshes, mode and length switches and broken storage, with a fair Give Up and a way to reset everything, **so that** I can come back to any game later without ever losing progress.

<objective>
Build the pure, test-first merge rules that make two tabs converge (CR-02, WR-04), as a TDD plan in `src/logic/save.ts`.

Design choice (Claude's discretion; the review's suggested fix extended): whole-document last-writer-wins cannot tell "a new game" from "a stale copy of the old game", and the review's "same answer keeps more guesses" fails when a new game happens to reuse the answer (always the case with the e2e fixed-answer hook). Each game therefore gets a small integer `id` (a per-tab Lamport-style counter, assigned in 04-10). Merging is then a pure max over a total order, which is commutative, associative and idempotent, so tabs always converge. No SAVE_VERSION bump: `id` is optional, and documents without it read as id 0.

Purpose: SAVE-08 (tabs stay in sync) and SAVE-09/CONTEXT ("never double-count a finished game; Phase 5 stats depend on this").
Output: new exports in save.ts with table-driven tests.
</objective>

<feature>
  <name>Per-Board merge with game ids</name>
  <files>src/logic/save.ts, src/logic/save.test.ts</files>
  <behavior>
    Types and validation:
    - SavedGame gains optional `id?: number`.
    - validateGame: when the input has an own `id` key, it must satisfy Number.isSafeInteger(id) && id >= 0, else the Board is invalid (same treatment as any other bad field); the output includes `id` only when the input had it. V1_FIXTURE (no ids) still validates to exactly itself; a fixture with `id: 3` round-trips with id 3; `id: -1`, `id: 1.5`, `id: '3'` are rejected.
    - gameIdOf(g) returns g.id ?? 0.
    - sameGame(a, b): both undefined -> true; one undefined -> false; else equal answer, outcome, guesses (joined) and gameIdOf.
    - maxGameId(boards) returns the highest gameIdOf over present Boards, 0 when empty.

    pickGame(a, b) (both defined), the winner in this order:
    - higher gameIdOf wins (new game beats old game, whatever their outcomes or answers)
    - same id, same answer: finished (outcome !== 'playing') beats 'playing'; then more guesses wins
    - same id, different answers (two tabs started a game at the same moment): the alphabetically lower answer wins
    - still tied and not identical: the one whose `outcome + ':' + guesses.join(',')` string sorts lower wins; identical -> returns a
    Cases: {id 1 crane [] playing} vs {id 2 crane [] playing} -> id 2; {id 2 slate [house] playing} vs {id 1 crane [house, crane] won} -> id 2 slate; {id 1 crane [house] playing} vs {id 1 crane [house, crane] won} -> won; {id 1 crane [house, ghost] playing} vs {id 1 crane [house] playing} -> 2 guesses; {id 1 crane [house] gave-up} vs {id 1 crane [house, ghost] playing} -> gave-up (finished never goes back to playing); {id 2 crane [] playing} vs {id 2 slate [] playing} -> crane; no ids vs no ids, same answer -> more guesses.
    Property: for every ordered pair in the case table, sameGame(pickGame(a, b), pickGame(b, a)) is true, and pickGame(a, a) is a.

    mergeBoard(mine, theirs, floor = -1):
    - theirs is ignored (treated as missing) when gameIdOf(theirs) <= floor
    - theirs missing -> mine (a document that lacks a Board never deletes it, CR-02)
    - mine missing -> theirs (after the floor check)
    - both -> pickGame(mine, theirs)
    Cases: (A, undefined) -> A; (undefined, B id 3, floor 5) -> undefined; (undefined, B id 6, floor 5) -> B; (A id 7, B id 3, floor 5) -> A.

    mergeBoards(mine, theirs, floor = -1): applies mergeBoard for each of BOARD_KEYS and returns a new object containing only keys whose merged value is defined, in BOARD_KEYS order. Does not mutate inputs.
  </behavior>
  <implementation>
    Pure functions in src/logic/save.ts next to validateSave; no imports from src/state. Comment above pickGame stating the total order and why it must be symmetric (two tabs must agree without talking). Keep validateSave's other rules unchanged (WR-05 is out of scope).
  </implementation>
</feature>

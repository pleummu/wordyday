# Phase 4 — UI Design Contract

> Visual and interaction contract for Six Boards and Persistence. Extends `03-UI-SPEC.md` and `02-UI-SPEC.md` (tokens, typography, spacing, motion, accessibility, Modal all still apply); only deltas are specified here. Generated by gsd-ui-researcher, to be verified by gsd-ui-checker.
> Sources: 04-CONTEXT.md D-01..D-16, SPEC.md R-BOARD / R-SAVE / R-FORFEIT, current `src/styles/tokens.css`, `game.css`, `Modal.tsx`, `Banner.tsx`, `LengthPicker.tsx`, `Header.tsx`, `Toast.tsx`.
> Items marked `[OWNER APPROVED]` were proposed copy or choices and were approved by the owner on 2026-10-02 (see Owner Decisions at the end). Copy locked by SPEC R-FORFEIT-3 / CONTEXT D-04 / D-07 / D-08 / D-09 is marked `[LOCKED]`.

## Scope

In scope: Give Up / New game row, their two confirm dialogs, the "gave up" banner variant, header Settings button, Settings modal, Reset confirm (destructive style), "All data reset" toast, in-progress dot on the length picker, storage-trouble feedback (corrupt data, blocked/full storage, other-tab change), removal of the Phase 3 "End this game?" switch confirm, restored-game presentation, and reduced-motion / keyboard / screen-reader rules for all of these.

Out of scope: stats, streaks, Restores (Phase 5), result modal and share (Phase 6), themes, colour-blind palette, help, credits (Phase 7). Tile, key, grid, switch and (i) styling are unchanged.

## Spacing Scale

Unchanged tokens (`--space-1..7` = 4, 8, 16, 32, 24, 48, 64). New usages:

| Token | Usage in Phase 4 |
|-------|------------------|
| `--space-1` (4px) | Gap between the in-progress dot and the segment edge is set by offsets below (6 px, see exceptions); gap between Settings note and button group |
| `--space-2` (8px) | Gap between the two Give Up / New game text buttons; gap between header row and forfeit row (existing `.app` gap) |
| `--space-3` (16px) | Horizontal padding of each text button; Settings body gap |
| `--space-5` (24px) | Modal padding (unchanged) |

Exceptions (intentional):

- Forfeit row is 32 px high with two text buttons. Hit area is 32 px high and at least 64 px wide. This is under 44 px and is accepted under the Phase 2 WCAG 2.5.8 exception (24 px minimum met). On viewports 640 px or taller the row height is 36 px (`min-height: 640px`) and gets 8 px more room automatically from the flex layout.
- In-progress dot is 6 px (a component size, not a spacing token), placed 6 px from the segment's top and right edges.
- Settings button: 32 px visual circle, hit area 40 x 40 (44 x 44 at 400 px and wider; 36 x 36 at max-height 540), same as the (i) button.

### 320 x 500 / 320 x 568 fit proof (replaces the Phase 3 budget when the row is visible)

The row is a flex sibling between `.board-area` and `.controls`, rendered only while exactly 2 tries are left and the game is `playing`. It adds 32 px plus one extra 8 px `.app` gap = 40 px.

- Rule: while the row is shown, `.app` sets `--tile-min: 36px` (was 40 px), and at `max-height: 540px` it stays `32px` (unchanged). This lets the grid absorb the row.
- 320 x 500 (max-height 540 applies): header 64, controls 124, gaps 3 x 8 = 24, row 32 = 244; grid area = 256 px. Worst case 6 letters / 7 rows: tile = (256 - 24) / 7 = 33 px (floor 32). Fits, no vertical scroll. Without the row the tile is 39 px, so tiles shrink by up to 6 px at the moment the row appears (it appears after the reveal ends, never during it).
- 320 x 568: header 80, controls 136, gaps 24, row 32 = 272; area = 296; tile = (296 - 24) / 7 = 38.9, so 38 px (floor 36 met). Fits.
- 320 x 640 and taller: key height 44 and controls 148; area = 640 - 80 - 148 - 24 - 36 = 352; tile = 46 px. Fits.
- Playwright (`e2e/layout.spec.ts`) must add a case that drives a 5-letter game to 4 guesses and asserts no vertical scroll and no horizontal overflow at 320 x 500, 320 x 568 and 320 x 640, in both Normal and Wordubado, for 6-letter (7 rows, tightest) too.

## Layout and Components

### Give Up / New game row (D-01, D-02)

```
[ grid ]
   Give up    New game        <- 32 px row, centred, quiet text buttons
[ keyboard ]
```

- Element: `<div class="forfeit-row">`, `display: flex; justify-content: center; gap: var(--space-2); height: 32px`, a sibling between `.board-area` and `.controls` in `App.tsx`. Two `<button type="button">`: "Give up" (first) then "New game".
- Buttons: `height: 32px; min-width: 64px; padding: 0 var(--space-3)`, Label 14/600, transparent fill, underlined, `border-radius: var(--radius-pill)`, `cursor: pointer`, `font-family: inherit`. No shadow.
- Visibility: rendered only when `status === 'playing'` AND `attemptsUsed === maxAttempts - 2` (R-FORFEIT-1/2). Not rendered (not disabled, not greyed, not `hidden`-toggled) at any other time: fresh board, other attempt counts, `revealing`, `loading`, `won`, `lost`, `gave-up`. It therefore also never shows on a finished Board (D-02). No transition; it simply mounts after the reveal ends.
- Both buttons carry `data-own-enter` (Enter activates the button and never submits a guess).
- Tab order: switch, (i), Settings, length picker, then keyboard keys. The row comes after the grid and before the keys in DOM order, so the full order is switch, (i), Settings, length picker, Give up, New game, keyboard keys.
- Hidden while a dialog is open (the whole app is `inert` already).

### Give Up and New game confirm dialogs (D-04, D-05)

Built on the Phase 3 `Modal` unchanged in structure. Same layout: heading 20/600, body 16/400, buttons right aligned (stacked full width, primary on top, below 400 px).

| | Give Up confirm | New game confirm |
|---|---|---|
| Heading `[OWNER APPROVED]` | Give up? | New game? |
| Body `[LOCKED]` | This counts as a loss. Reveal the answer? | This counts as a loss. Start a new game? |
| Secondary (cancel, initial focus) | Keep playing | Keep playing |
| Primary (sage) | Give up | New game |

- Initial focus is "Keep playing" (safer default; Phase 3 rule). Esc and scrim click cancel. Cancel returns focus to the row button that opened it.
- On confirm, the Modal closes with its 120 ms close, then:
  - Give Up: the game is marked finished as `gave-up`, the loss banner variant appears in the keyboard slot, "Play again" takes focus (existing Banner behaviour). No row is added to the grid (D-03). Key colours do not change and no flip plays.
  - New game: the forfeit is recorded as a loss, a new game starts at once on the same Board (new answer, empty grid, keyboard back). Focus goes to the page body (physical keyboard resumes), same as Play again. No toast.
- The Phase 3 `SwitchConfirm` is deleted (D-05). Mode and length switches are immediate and non-forfeiting; no dialog, no toast. The Phase 3 confirm copy ("End this game?", "Start new game") must not appear anywhere after this phase. The only "Start new game"-like string left is the New game button above.

### "You gave up" banner variant (D-03)

Same `.banner` markup, `data-result="gave-up"`, same `--color-error` 1 px border and `min-height: var(--controls-h)` as `lost` (no layout change, no new animation).

| Part | Copy |
|------|------|
| Heading (Heading 20/600) | The word was {ANSWER} (uppercase answer, same as the loss banner) |
| Body (Label 14/600) `[OWNER APPROVED]` | You gave up. Ready for another? |
| Button | Play again |

Rationale: the answer stays the loud part; "You gave up" replaces the "Better luck next time." wording. `aria-live="polite"` is kept so the banner is announced.

Restored finished games (all of won, lost, gave-up) render the grid and banner statically on load: no flip, no bounce, no win toast, and the banner does NOT auto-focus "Play again" (that focus move only happens when the game finishes in-session; on a restore, focus stays on the page body so a screen-reader user hears the page, not a surprise jump). The Banner `useEffect(() => focus())` must be gated on "finished in this session".

A game forfeited via New game shows no banner (the new game replaces it), per CONTEXT.

### Header: Settings button (D-06)

- Element: `<button type="button" aria-label="Settings" aria-haspopup="dialog" data-own-enter>` containing the sliders SVG (18 px) inside `.header-actions`. Shown now (remove `display: none`). Icon colour `--color-text` in both modes (not mode-tinted), hover fill `--color-surface`, focus ring as all controls. Enabled while `revealing` (opening Settings never touches the game; Phase 3 D-17 precedent).
- Placement:
  - at 400 px and wider: `.header-top` is `justify-content: space-between`; title left, Settings button right-aligned (existing rule).
  - below 400 px: the title stays centred (Phase 3 look unchanged). The `.header-actions` slot is positioned absolutely at the right edge of `.header-top` (`position: absolute; right: 0; top: 50%; transform: translateY(-50%)` with `.header-top { position: relative }`). Title is about 168 px wide in a 288 px row, so there is 60 px each side and the 40 px button fits with no overlap at 320 px.
  - Phase 5 (Stats) and Phase 7 (Help) add more buttons; when they land, below 400 px the actions slot should wrap beneath the title or share row 2. Not solved here; noted so Phase 5 revisits.
- Short viewports (`max-height: 540px`): button is 36 x 36, icon 16 px, row stays 24 px high (the button may overflow the 24 px title row by design since it is absolutely positioned / centred; it must not increase header height. Verify the 64 px header total at 320 x 500).
- Enter on this button opens Settings, because it has `data-own-enter`. Phase 3 recorded that Enter on the header mode switch submits the guess; that is unchanged for the switch and (i) (WR-05 is deferred to Phase 7). The new Settings button deliberately uses the correct behaviour from day one.

| Part | Copy / style |

## Storage-trouble feedback (Claude's discretion, decided here)

Principles: calm, short, never blocking, never a dialog, game always playable. Every message is an info toast (`role="status"`, polite, never `alert`) or stays silent. Toast text is Label 14/600 in the existing toast style.

Toast change (needed by this section only): `ToastData` gets an optional `lifeMs` (default `1860`). The `Toast` timer uses it, and CSS sets `animation-duration: calc(var(--toast-life, 1860) * 1ms)` via an inline `--toast-life`. The percentage keyframes scale (fade in about 8.6 percent, out the last 10.8 percent), which is fine. Reduced motion keeps the opacity-only variant. Long toasts use 4000 ms.

| Situation | Decision |
|-----------|----------|
| Corrupt or invalid saved data, backed up to `:corrupt` and reset (R-SAVE-2) | Show once at startup: "We couldn't read your saved games, so we started fresh." info toast, `lifeMs` 4000. The player lost progress and should know it was not their doing; no instructions needed (the backup is a developer safety net, not a user feature). Do not show for a first visit (no data) or for a normal migration. |
| localStorage blocked, unavailable or full (R-SAVE-3) | Show once per page session, on the first failed read or write: "Saving isn't working in this browser. Your progress will be lost when you close this tab." info toast, `lifeMs` 4000. Never repeat on later failed writes. No message when storage recovers. While it is failing, the Settings modal also shows the storage-off line (above) so the state is discoverable on demand. The game stays fully playable in memory. |
| Another tab changes the active Board (R-SAVE-4) | Rule: last write wins. The `storage` handler re-reads the document and compares only the Board this tab is showing. If its answer, submitted guesses or status differ, replace the in-memory Board with the saved one (any half-typed row is dropped) and show "Updated from your other tab." info toast (default 1860 ms). If only other Boards changed, or nothing visible changed, stay silent. The tab does not follow the other tab's "last active Board" pointer (that would flip this tab's Board while the player looks at it); the pointer is read only on load. If a reveal is running, defer applying the update until it finishes. If a dialog is open, apply the data underneath and leave the dialog open. If the other tab reset all data, apply the same rule (this tab becomes the first-visit state) with the same toast. Never double-count a finished game: the finished status is applied from storage, it is not re-finished locally. |
| Reset | "All data reset" (info, 1860 ms) as D-09. |
| Pool-load retry (D-15) | If `navigator.onLine` is false the existing Phase 2 error banner and "Try again" stay; no reload, no extra message. |

Only one toast is shown at a time (a newer toast replaces the older one instantly, Phase 2 rule). A startup storage toast can therefore be replaced by an early "Not enough letters" toast; that is accepted.

## Interaction Rules

- Mode or length change: always immediate. A Board with a saved game shows it as it was; a Board with no saved game starts a new game at once (D-13). Switching is blocked only while `status === 'revealing'` (Phase 2/3 rule, controls show `aria-disabled`). The switch confirm is gone (D-05).
- On load, open the last Board the player played (D-10); first ever visit is Normal 5.
- Refresh: submitted guesses are restored; any half-typed letters are gone (R-BOARD-3). A restored in-progress grid renders statically with key colours already applied; the keyboard is disabled until the pool for that length is loaded (same loading rule as Phase 2, "Loading words..." after 400 ms).
- Give Up / New game are the only way to abandon a game in progress and exist only at exactly 2 tries left. A fresh Board cannot be abandoned (R-FORFEIT-6).
- Finished Board: grid, banner (won, lost, gave up) and Play again; no forfeit row.
- One dialog at a time (Phase 3 rule). The sequence Settings to Reset confirm to back to Settings is the only chained flow.
- Modal `close` event (D-14): if the browser closes a `<dialog>` without a `cancel` event (Esc without recent user activation, Android back gesture), the `Modal` must handle the native `close` event and call the same close handler, so the store never keeps a dialog "open" with all keys ignored. Focus returns to the opener as usual.
- First switch to Wordubado ever: the "What's Wordubado?" popup auto-opens once, using the saved flag (D-11); reset clears it. No change to its copy.
- Reveal timers are tied to a game token (D-16): a reset, Board switch, New game or restore during a reveal must not let a stale timer end the wrong game (no visible change except correctness).

## Animations and Reduced Motion

- New elements add no new keyframes: the forfeit row, dot, Settings button and gave-up banner mount without animation.
- Dialogs: unchanged Phase 3 behaviour (160 ms scale + fade in, 120 ms fade out; reduced motion: 120 ms opacity in, instant out).
- Toasts: unchanged; the long toast uses the same opacity and 8 px translate fade, and under `prefers-reduced-motion: reduce` the existing opacity-only `toast-fade` keyframes apply with the scaled duration.
- Restored games never animate on load (no flip, bounce, pop, shake, win toast).
- Reduced motion: nothing new needs an override beyond the long-toast duration variable. Tile floor shrink when the forfeit row mounts is instant, not animated.

## Accessibility (additions)

- Forfeit buttons: native buttons named "Give up" and "New game", `data-own-enter`, 32 px targets (accepted under 2.5.8), underlined so they are not colour-only.
- Settings button: `aria-label="Settings"`, `aria-haspopup="dialog"`, `data-own-enter`, 40/44 px target.

- Physical keyboard: `usePhysicalKeyboard` already ignores keys while `dialog[open]`; Enter on the forfeit buttons and the Settings button is handled by `data-own-enter`. The mode switch keeps the Phase 3 behaviour (Enter submits the guess, Space toggles).
- Contrast: forfeit text `--color-text` on `--color-bg` about 13:1; `--color-danger` text on `--color-bg` about 5.3:1; `--color-bg` text on `--color-danger` fill about 5.3:1; dot `--color-text` on `--color-surface` about 12:1.
